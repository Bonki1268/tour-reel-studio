# 觀光業者 AI 宣傳影片系統 — 構想文件

> 名稱：Tour Reel Studio（repo：`tour-reel-studio`）
> 文件版本：v0.3（2026-09-28）— 新增快速模式、AR 實景融合

---

## 1. 產品定位

**一句話**：讓觀光業者「一個網址或幾句描述」開始，一步步做出屬於自己品牌、可系列化、以真實場景為基礎的 AI 宣傳短片。

**首發規格**：鎖定 **IG Reels 15 秒短影片**（9:16）。

**目標使用者**：民宿、農場、老街店家、小型觀光工廠、地方導覽業者。共同特徵是有故事、沒預算請團隊、沒時間學習 AI 影片工具與剪輯軟體。

### 1.1 要解決的痛點

| 痛點 | 說明 | 系統對策 |
|---|---|---|
| 不會下提示詞 | AI 工具的門檻在「怎麼描述」，不在「按按鈕」 | 選項式引導，用選擇取代撰寫 |
| 結果不可控 | 一次生成，不滿意只能整個重來 | 逐關確認、逐鏡重生 |
| 無法系列化 | 每次生成的角色、畫風都不同 | 角色定妝、場景板、專案資產庫 |
| 不夠真實 | AI 畫出的景點與實際不符 | 實景融合 |
| 不知道自己的賣點 | 業者難以跳出自身角度 | 商家洞察：自動蒐集官網、評論、社群 |

## 2. 核心設計原則

### 2.1 用選擇取代撰寫
使用者不寫提示詞。系統把描述轉成選項，例如：
- 影片調性：溫馨家庭／懷舊職人／活潑年輕
- 主角：老闆風格角色／虛構吉祥物／遊客視角
- 開場鉤子：美景震撼／角色搭話／反差驚喜

每題都保留「其他，我自己說」。影片規格固定為 IG Reels 15 秒，不需使用者選擇。

### 2.2 先便宜、後昂貴的確認關卡
```
文字企劃 → 腳本與對白 → 角色定妝＋場景板確定 → 分鏡靜態圖 → 單鏡頭影片 → 整片合成
```
每一關都比前一關貴。方向在文字與圖片階段就定下來，影片階段失敗率與成本都降低。重生以**鏡頭**為單位，不必整片重來。

**進入分鏡的門檻**：腳本中所有出場角色都已鎖定定妝版本、所有場景都已確認場景板，才能開始分鏡。分鏡關鍵幀一律引用已鎖定的角色與場景版本，避免分鏡階段才發現角色或背景需要重做，連帶讓已確認的分鏡全部失效。

### 2.3 一切經使用者同意
- 每個階段狀態：草稿 → 待確認 → 已核准 → 生成中 → 完成
- 未核准不能進下一步（快速模式中，部分關卡由系統代為核准，見 2.5）
- 內容一旦修改，先前的確認即失效
- 系統自動蒐集的資料，也必須經業者確認才採用
- **花錢的步驟一定要使用者確認**：兩種模式都會在生成影片前顯示預估點數

### 2.4 資產可重用
品牌檔案、角色、場景、畫風都是**專案內的資產**，專案裡的每支影片都共用，讓產品從一次性工具變成持續經營品牌的平台。

### 2.5 快速模式與進階模式
「高度掌控」與「上手簡單」本質上有衝突，因此提供兩種模式，由使用者在每支影片開始時選擇：

| | 快速模式 | 進階模式 |
|---|---|---|
| 適合 | 想快速出片的業者 | 想逐步掌控細節的業者 |
| 確認點 | 2 個：企劃（含預估點數）、成品 | 每個階段都確認（見 3.2） |
| 其他階段 | 系統自動採用建議方案 | 使用者逐步審核 |
| 切換 | 任何時候可「展開進階」，已完成的步驟全部保留 | — |

兩種模式跑的是**同一條流程、同一份資料**，差別只在哪些關卡由系統自動核准。自動核准的項目在紀錄中標示「系統自動採用」，使用者事後都能回頭修改。

## 3. 使用者流程

流程分兩段：**建立專案**只做一次，**製作影片**在專案內可重複進行。

### 3.1 建立專案（一次）
```
⓪ 建立專案：輸入店名／網址／粉專連結（任一即可）
   └ 確認身分：「是這一家嗎？」（顯示地圖位置與照片）
① 商家洞察：背景蒐集（非同步，完成推播）
② 品牌檔案確認：逐項卡片確認 → 成為本專案的品牌檔案
③ 勘景：MVP 上傳 3–5 張實景照（素材入庫，供之後所有影片使用）；第二階段加入 AR 取景
```

### 3.2 製作影片：進階模式（每支）
```
④ 特色訪談：這支影片想強調什麼（品牌檔案已預填，只需補充）
⑤ 企劃方向：2–3 案選 1 或混合
⑥ 腳本與對白：15 秒、3–5 鏡，逐鏡可改、可換版本
⑦ 角色與背景確定（進入分鏡的門檻）
   ├ 角色定妝：沿用專案內角色，或 候選造型 → 身份板 → 鎖定
   └ 場景板：依腳本需要的場景，從實景照或 AR 取景建立
   ※ 腳本中所有角色與場景都鎖定後才能進入下一步
⑧ 分鏡關鍵幀：逐格確認，選擇實景融合模式（可用 AR 現場擺放角色）
⑨ 生產預覽：顯示鏡數、參考圖、使用模型、預估點數 → 確認
⑩ 逐鏡生成（Higgsfield API）：單鏡可重生，完成推播通知
⑪ 自動合成：拼接、字幕、配樂、片尾資訊
⑫ 輸出：於專案介面調整語言與比例後匯出
⑬（擴充）時間軸編輯器
```

### 3.3 製作影片：快速模式（每支）
```
④ 一句話：「這支想宣傳什麼？」（可直接點選品牌檔案中的賣點）
⑤ 企劃確認 ✋：3 案選 1，每案附 3 格示意圖與預估點數
      ↓ 系統自動完成（背景執行，完成推播）
      ├ 腳本與對白：採用建議版本
      ├ 角色：沿用專案內已鎖定角色；需要新角色時採用第一候選，標為「暫定定妝」
      ├ 場景：從已入庫的實景照自動挑選
      ├ 分鏡：自動產生，預設使用實景合成
      └ 逐鏡生成＋自動合成
⑥ 成品確認 ✋：
      ├ 滿意 → 匯出
      ├ 某一鏡不滿意 → 單鏡重生（顯示點數後確認）
      └ 想細調 → 展開進階模式，從任一步驟修改
```

**設計重點**
- 預估點數合併在企劃確認中顯示，確認企劃即同意這次生成的費用上限；若重生會超出上限，再次詢問。
- 「暫定定妝」的角色可以在成品確認後一鍵鎖定，之後的影片就能沿用，維持系列一致。
- MVP 的 Demo 專案預先備妥 3–5 張實景照；正式版若尚無照片，先引導業者上傳至少 3 張。AR 取景引導為第二階段功能。

## 4. 功能模組

### 4.0 影片規格：IG Reels 15 秒

| 項目 | 規格 |
|---|---|
| 長度 | 15 秒 |
| 比例 | 9:16（預設，可於專案介面調整） |
| 鏡頭數 | 3–5 鏡，每鏡約 3–5 秒 |
| 結構 | 開場鉤子（前 1–2 秒）→ 特色展示 → 結尾行動呼籲（地點、訂位方式） |
| 字幕 | 預設開啟（多數人靜音滑 Reels） |

15 秒的限制讓每支影片的生成成本與確認次數都可控，也最適合競賽現場 Demo。

### 4.1 商家洞察（Brand Intelligence）

**在建立專案時執行**，產出的品牌檔案屬於該專案，專案內所有影片共用。業者只需確認。

#### 資料來源

| 來源 | 取得方式 | 取得內容 | 用途 |
|---|---|---|---|
| 官方網站 | Firecrawl（branding format＋內容擷取） | Logo、品牌色、字型、介紹文案、服務項目 | 片尾、字幕樣式、視覺方向 |
| Google 地圖 | Google Places API | 評論、評分、營業時間、地址、照片 | 歸納遊客喜愛的賣點、片尾資訊 |
| FB／IG | Meta 官方 API，**業者本人授權登入** | 貼文文案、熱門貼文、照片影片、成效 | 分析品牌語氣、實景素材 |
| 網路口碑 | Firecrawl search | 部落客遊記、旅遊網站介紹 | 補充外部觀點與在地故事 |

> 社群平台條款禁止爬取，一律透過業者授權的官方 API 讀取。

#### 產出：品牌檔案

1. **視覺識別**：Logo、主色／輔色、字型 → 片尾、字幕、角色服裝配色
2. **特色賣點**：由評論與介紹歸納（如「早餐手作、老闆熱情、夕陽景觀」）→ 企劃選項素材
3. **品牌語氣**：親切台味／文青質感／熱鬧活潑 → 對白風格與角色聲音
4. **基本資訊與素材**：地址、營業時間、訂位方式、既有照片 → 片尾資訊、實景候選素材

確認介面以卡片呈現「我們發現⋯⋯對嗎？」，每項可保留／刪除／修改。

品牌檔案可在專案設定中手動編輯，或重新執行蒐集（例如新菜單、新評論），有變動時提醒業者確認。

### 4.2 角色定妝（每個角色必備）

每個角色建立時先完成定妝包，**鎖定後才能進入分鏡**。角色存在專案內，同專案的其他影片可直接沿用。

| 項目 | 內容 |
|---|---|
| 身份板 | 正面、側面、背面全身三視圖，純色背景；作為所有後續生成的參考圖 |
| 表情表 | 開心、介紹、驚喜、沉思等宣傳片常用表情 |
| 身份錨點卡 | 不可變動特徵（臉型、髮型、代表配色、配件），每次生成自動附加 |
| 造型變體 | 季節版、節慶版、工作服版；只改允許變動的部分 |
| 聲音設定 | 語氣、年齡感、口音 |

**流程**：候選造型（3 選 1）→ 生成身份板 → 逐項確認 → 鎖定為 v1。
**版本規則**：修改不覆蓋，另存新版本或新增造型變體；舊影片仍指向當時使用的版本。

**一致性策略**
- 身份板作為每次生成的參考圖
- 身份錨點卡固定附加於提示詞
- 同一專案鎖定畫風設定
- 分鏡圖確認後作為影片首幀，減少漂移

### 4.3 實景融合（AR 化）

實景融合的最大風險是「穿幫」：角色大小不對、站在半空中、光線方向和背景不一致。**MVP 先以照片合成（B1）驗證內容流程與圖生影片品質**；後續再讓業者在現場用手機 AR 把角色放進真實空間，取得更可靠的位置、比例、視角與光線資訊。

#### 模式總覽

| 模式 | 做法 | 階段 |
|---|---|---|
| A. 實景重繪 | 以實景照為參考，AI 重新生成場景，保留地理結構與地標，統一品牌畫風 | 第二階段 |
| B1. 照片合成 | 在已上傳的實景照上拖拉、縮放角色，決定位置後由 AI 合成關鍵幀 | MVP（不在現場時使用） |
| **B2. AR 取景合成（第二階段主力）** | 在現場開啟相機，角色以 AR 站在真實地面上；業者走位、調整角色位置與朝向後拍下 → AI 精修合成 → 圖生影片 | 第二階段 |
| C. 實拍＋AI 混剪 | 業者實拍片段與 AI 鏡頭交錯排在時間軸上 | 第二階段 |
| D. AR 動態實拍 | 業者邊走邊錄，AR 角色跟著真實運鏡；錄下的影片交給 AI 把替身換成定妝角色 | 第三階段（實驗性） |

#### B2 AR 取景合成流程

```
1. 開啟 AR 相機，偵測地面
2. 角色定妝的全身圖以「立牌」形式站在地面上
   （可拖曳位置、縮放、旋轉朝向、切換表情或姿勢）
3. 業者移動手機找角度，畫面上即時看到構圖
4. 按下快門，系統同時記錄：
   ├ 相機畫面（乾淨的實景，不含角色）
   ├ 角色在畫面中的位置、大小、腳底接地點
   ├ 相機高度與角度
   └ 環境光估計（光線方向、強度、色溫）
5. AI 以「乾淨實景＋角色身份板＋位置遮罩＋光線資訊」合成關鍵幀
6. 使用者確認 → 作為首幀圖生影片
```

**為什麼比單純照片合成好**
- **比例正確**：AR 知道真實尺寸，角色不會比門還高或像玩具
- **接地正確**：角色腳底對齊偵測到的地面，不會飄浮
- **光線一致**：AR 框架提供的環境光估計，可轉成提示詞中的光線描述，減少合成感
- **所見即所得**：業者在拍攝當下就看到構圖，對成品的掌控感最直接

**技術選擇**
- 行動端 AR：iOS 使用 ARKit、Android 使用 ARCore
- MVP 用 2D 立牌（定妝全身圖去背）即可，不需要 3D 模型；之後可選擇以圖生 3D 做成可轉身的立體角色
- AR 取景的資料存入場景板，之後的影片可重複使用同一個機位

#### 配套設計
- **勘景引導**：引導業者拍攝入口、主要景點、特色角落；避開人群；同一地點拍白天與黃昏
- **場景板**：每個地點存實景照、AR 取景紀錄（機位、地面、光線）、白天／黃昏／夜晚版本，供專案內所有影片重用
- **真實性標記**：每個片段標記「實拍／實景合成／AI 生成」，輸出時可選擇於片尾註明

### 4.4 創作流程引擎：drama-skills

採用開源 [zenstory-ai/drama-skills](https://github.com/zenstory-ai/drama-skills)（MIT 授權）作為創作流程引擎。它以每集 5 份 Markdown 為單一內容來源：`剧本.md`、`视觉设定.md`、`分镜.md`、`图片提示词.md`、`视频提示词.md`，並規定生產前必須展示精確任務並取得明確確認，與本系統的核准原則一致。本系統中「一集」對應「一支影片」。

#### 技能與 App 步驟對應

| App 步驟 | Skill | 產物 |
|---|---|---|
| 企劃方向 | `short-drama-develop` | 故事引擎、企劃方向 |
| 腳本與對白 | `short-drama-write` | 剧本.md |
| 角色／場景拆解 | `short-drama-assets` | 视觉设定.md |
| 角色定妝、場景板 | `short-drama-image-prompts` | 身份板、造型變體、地點板提示詞 |
| 分鏡關鍵幀 | `short-drama-storyboard` | 分镜.md、冻结关键帧 |
| 逐鏡影片 | `short-drama-video-prompts` | 视频提示词.md |
| 確認後生產 | `short-drama-produce` | 呼叫 Higgsfield API 並記錄結果 |
| 品質檢查 | `short-drama-review` | 審查結論 |

#### 整合所需工作

1. **後端 Agent 執行**：以 Claude Agent SDK 為每個專案建立獨立工作目錄，由 Agent 讀寫 Markdown；使用者不接觸 CLI。
2. **Markdown ↔ App 轉譯層**：Agent 需要決策時輸出結構化選項（JSON），前端渲染為選項卡片，選擇結果回傳 Agent。
3. **Higgsfield adapter**：drama-skills 內建 Seedance、GPT Image 2、MiniMax Music 的 adapter，需依其介面撰寫 Higgsfield 版本。Higgsfield 平台也提供 Seedance 系列模型，可參考原有 Seedance adapter 的參數結構。
4. **觀光題材擴充 `tourism-promo` skill**：原套件針對短劇／漫劇設計，需補上 IG Reels 15 秒宣傳片的節奏（開場鉤子、3–5 鏡、結尾行動呼籲）、體驗與氛圍導向，並統一輸出繁體中文。
5. **品牌檔案注入**：專案的品牌檔案存為工作目錄中的 `品牌檔案.md`，供故事開發、資產拆解與 Look Development 讀取。

### 4.5 影片生成：Higgsfield API

Higgsfield 以單一 API 提供多家影片與圖像模型，採非同步請求（回傳 request ID，以輪詢或 webhook 取得結果），並提供 Python 與 TypeScript SDK。

**模型策略**：由 adapter 包裝，不在程式中寫死特定模型。依驗證結果（見第 9 節）挑選：

| 需求 | 候選模型（Higgsfield 上提供） | 備註 |
|---|---|---|
| 對白＋原生音訊 | Kling 3.0／2.6、Wan 3.0、LTX 2.5 | 需實測中文對白品質 |
| 首幀／尾幀控制（模式 B1／B2） | Kling O3、Kling O1、PixVerse 6 | 以確認後的分鏡圖為首幀 |
| 跨鏡角色一致 | Wan 2.7、Kling O3（參考圖輸入） | 搭配定妝身份板 |
| 定妝圖、實景合成圖 | Higgsfield 圖像模型（如 Grok Imagine 2.0 的精準編輯） | 需實測實景合成效果 |

**注意事項**
- 生成結果在 Higgsfield 端保留期間有限，完成後應立即下載存入自有物件儲存。
- webhook 回呼觸發後端狀態機更新並推播通知使用者。

### 4.6 合成與輸出設定

- **自動合成**：FFmpeg 依時間軸 JSON 拼接、加字幕、背景音樂、片尾（Logo、地址、QR code）
- **輸出設定面板（專案介面）**：使用者自行調整，不在生成流程中詢問

| 設定 | 預設 | 說明 |
|---|---|---|
| 比例 | 9:16 | 其他比例（1:1、16:9）以重新構圖裁切產出；構圖不佳的鏡頭可選擇重生 |
| 字幕語言 | 中文 | 切換只需重新翻譯字幕，成本低 |
| 配音語言 | 中文 | 切換需重新生成含對白的鏡頭，執行前顯示預估點數並確認 |

語言與比例設定存在專案層級，可設為該專案的預設值，也可在單支影片匯出時覆寫。

### 4.7 擴充：時間軸編輯器（類 CapCut）

從第一天起，影片即以**時間軸資料結構**儲存，而非只存 mp4。編輯器只是「修改這份 JSON 的介面」，不需重構。每個片段都連回其鏡頭、腳本與生成參數，因此可支援「對這段按右鍵 → 用 AI 重生」。

## 5. 系統架構

```
[Web 前端（MVP）／行動 App（第二階段）]
    │  專案管理／選項卡片／圖片確認／生產預覽／輸出設定
    │  MVP：實景照上角色擺放（B1）；第二階段：AR 取景模組（ARKit／ARCore）
[後端 API + 工作流程狀態機]
    │
    ├─[品牌資料來源]
    │   ├─ MVP：手動輸入＋預先擷取的官網內容 → 品牌檔案（待確認）
    │   └─ 第二階段：Firecrawl、Google Places API、Meta Graph API → LLM 彙整
    │
    ├─[創作引擎]
    │   ├─ MVP：Claude API＋tourism-promo 受控 prompt／JSON
    │   └─ 第二階段：Claude Agent SDK＋drama-skills＋Markdown 工作目錄
    │
    ├─[生產轉接層]（模型可替換）
    │   ├─ Higgsfield adapter（MVP：圖像＋無音訊圖生影片）
    │   │    └─ 非同步請求 → webhook → 下載存檔
    │   └─ FFmpeg 合成服務（MVP：9:16、繁中字幕、配樂、固定片尾）
    │
    └─[資料庫 + 物件儲存]
```

### 5.1 兩層資料

| 層 | 格式 | 使用者 |
|---|---|---|
| 創作層 | Markdown（drama-skills 格式） | Agent 讀寫 |
| 剪輯層 | 時間軸 JSON | 合成服務、未來編輯器 |

生產完成時，由系統將 Markdown 中的鏡頭結果轉寫為時間軸 JSON。兩層分離，drama-skills 升級不影響編輯器，編輯器擴充也不必改動 Agent。

### 5.2 資料模型

```
使用者（業者帳號）
 └─ 專案（建立時執行商家洞察）
     ├─ 品牌檔案（視覺識別、賣點、語氣、基本資訊）
     ├─ 角色 → 定妝版本（v1, v2…）→ 造型變體
     ├─ 場景板 → 實景照、AR 取景紀錄（機位、地面、光線）、光線版本
     ├─ 畫風設定
     ├─ 輸出設定（預設比例、字幕語言、配音語言）
     └─ 影片（IG Reels 15 秒）
         ├─ Markdown 工作檔
         ├─ 鏡頭 → 版本（全部保留，可回溯）
         └─ 時間軸 JSON
```

### 5.3 時間軸 JSON 範例

```json
{
  "project_id": "p001",
  "video_id": "v003",
  "duration": 15.0,
  "output": { "aspect_ratio": "9:16", "subtitle_lang": "zh-TW", "voice_lang": "zh-TW" },
  "style": { "primary_color": "#C8553D", "font": "Noto Sans TC" },
  "tracks": [
    { "type": "video", "clips": [
      { "shot_id": "s1", "asset": "clip_s1_v2.mp4", "source": "ai_composite", "provider": "higgsfield", "start": 0, "duration": 3.0 },
      { "shot_id": "s2", "asset": "real_s2.mp4", "source": "real_footage", "start": 3.0, "duration": 4.0 },
      { "shot_id": "s3", "asset": "clip_s3_v1.mp4", "source": "ai_composite", "provider": "higgsfield", "start": 7.0, "duration": 5.0 },
      { "shot_id": "s4", "asset": "outro_card.mp4", "source": "template", "start": 12.0, "duration": 3.0 }
    ]},
    { "type": "subtitle", "items": [
      { "text": "歡迎來到梅子農場", "start": 0.3, "end": 2.8 }
    ]},
    { "type": "audio", "clips": [
      { "asset": "bgm_warm_01.mp3", "start": 0, "volume": 0.3 }
    ]}
  ]
}
```

`source` 欄位對應真實性標記：`real_footage`／`ai_composite`／`ai_generated`／`template`。

## 6. 競賽亮點

### 6.1 差異化

| 對比對象 | 他們的問題 | 本系統 |
|---|---|---|
| 直接使用 AI 影片工具 | 需會寫提示詞、結果不可控 | 選項式引導、快速／進階兩種掌控程度 |
| CapCut／Canva | 需自備素材、自己剪輯 | 素材依業者特色生成 |
| 委託廣告公司 | 昂貴、耗時 | 低成本、可持續自行產出 |

### 6.2 可強調的賣點
- **「一句話，做出一支 Reels」**：選擇企劃、確認成本，即可開始生成
- **實景照片融合**：將已定妝角色放入業者提供的真實景點照，讓畫面保有地點辨識度
- **快速模式**：只保留企劃與成品兩個確認點，降低非技術業者的操作門檻
- **固定品牌角色**：以一個已定妝角色維持影片內的視覺一致性
- **專注 IG Reels 15 秒**：符合觀光業者最主要的宣傳管道
- **成本透明**：生成前顯示本次預估點數與費用上限

### 6.3 Demo 建議
現場以一家預先準備資料的真實民宿建立專案，確認品牌檔案後，以一句話選擇宣傳主題。使用已上傳的實景照，在 Web 介面拖拉、縮放已定妝角色完成 B1 照片合成，確認企劃與成本後生成 15 秒 Reels。最後展示同一專案中可沿用的角色與場景資產；AR 取景則以錄製影片說明為第二階段能力。

### 6.4 開源使用聲明
「本系統採用開源 drama-skills 作為創作流程引擎，並自行開發觀光題材擴充、Higgsfield 生產轉接層、品牌檔案確認流程與實景照片融合介面；AR 實景融合與行動端介面為後續擴充。」

## 7. 風險與對策

| 風險 | 對策 |
|---|---|
| 生成成本高 | 15 秒短片、先圖後影、逐鏡重生、預估點數透明化；蒐集結果快取 |
| 角色一致性 | 定妝身份板＋錨點卡＋畫風鎖定＋確認後首幀 |
| 聲音跨影片一致性 | 所選模型的原生音訊需實測；若不足，為系列角色保留 TTS 選項 |
| 單一供應商依賴 | Higgsfield 包在 adapter 後，必要時可替換或直連模型原廠 |
| 生成結果保存期限 | 完成後立即下載存入自有儲存 |
| 不實宣傳 | 實景融合、真實性標記、AI 生成標示 |
| 肖像權 | 以真人為角色原型時需本人同意機制 |
| 音樂版權 | 使用授權曲庫 |
| 照片權利 | 僅使用業者官網或授權社群帳號照片；第三方照片僅作參考 |
| 評論隱私 | 只保留歸納主題，不存評論者姓名與原文 |
| API 使用條款 | 社群平台一律走官方 API；Google Places 資料遵守快取與儲存限制 |
| 同名商家誤判 | 蒐集前先讓業者確認身分 |
| drama-skills 題材差異 | 自寫 tourism-promo skill；輸出轉為繁體中文 |
| 生成等待時間 | 非同步任務、webhook、推播通知；失敗重試前需重新確認 |
| 流程太繁瑣 | 快速模式只保留企劃與成品兩個確認點 |
| 快速模式品質不穩 | 自動採用項目可事後修改；單鏡重生；可隨時展開進階模式 |
| AR 需要到現場 | 業者本來就在現場；不在現場時改用 B1 照片合成 |
| 裝置不支援 AR | 偵測不到 ARKit／ARCore 時自動改用 B1 |
| AR 立牌是 2D | 只用於決定位置與比例，最終畫面由 AI 重新合成；側面角度可切換定妝的側面圖 |

## 8. 開發範圍

### 8.1 MVP（競賽展示）
- **單一介面**：Web 前端；不開發原生行動 App、ARKit／ARCore 或現場取景。
- **單一路徑**：快速模式；使用者輸入一句宣傳主題，從 2–3 個企劃中選一案，確認成本後生成成品。進階模式僅保留為 wireframe，不實作。
- **受控資料來源**：以手動輸入的店家資料與預先準備的官網內容建立品牌檔案；不串 Google Places、Meta 或網路搜尋，避免 API 審核、額度與現場網路風險。
- **固定資產組合**：每個 Demo 專案只支援 1 個已定妝角色與 3–5 張已上傳實景照；不做候選角色、造型變體、勘景流程或資產跨專案共用。
- **單一實景方式**：B1 照片合成。使用者在照片上指定角色位置與大小，產生一張關鍵幀後作為圖生影片首幀；不做 B2 AR 取景、A 實景重繪或 C 實拍混剪。
- **最小創作工作流**：以 `tourism-promo` 模板輸出 15 秒、3 鏡的固定結構（鉤子→特色→行動呼籲）。可先以後端受控 prompt／JSON 實作，drama-skills 整合只保留一條成功路徑。
- **單一生成供應商與模型組合**：封裝最小 Higgsfield adapter，只支援已驗證的一種圖像模型與一種圖生影片模型；不做模型選擇介面、語音生成或多供應商備援。
- **最小輸出**：FFmpeg 合成 9:16、15 秒 MP4，含繁中燒錄字幕、背景音樂與固定片尾。比例切換、多語字幕與配音不列入 MVP。
- **最小資料與可靠性**：保存專案、資產、企劃、鏡頭、生成工作與成品 URL；每個生成工作保留輸入快照、成本上限與外部 request ID。時間軸 JSON 可保存，但不提供編輯器。
- **Demo 成功定義**：從選題到輸出在 10 分鐘內完成；同一預備專案穩定輸出一支可播放的 Reels，且單鏡失敗可重試一次。

### 8.2 第二階段
- 完整商家洞察：Google Places、Firecrawl 搜尋、FB／IG 業者授權串接
- 進階模式：逐步審核腳本、角色、場景與分鏡；支援單鏡重生與核准失效規則
- 資產庫：多角色、候選定妝、造型變體、場景板與跨影片重用
- 實景融合模式 B2（AR 取景合成）與 C（實拍＋AI 混剪）；先完成單一原生平台驗證，再擴至另一平台
- 配音語言切換、多語字幕與其他輸出比例
- 簡易編輯器：剪裁、換順序、改字幕、換配樂
- 其他影片長度（30／60 秒）

### 8.3 第三階段
- 完整時間軸編輯、片段內 AI 重生
- 實景融合模式 D：AR 動態實拍＋AI 角色替換
- 直接發布至 IG／FB／YouTube
- 成效數據回饋：依觀看表現反向推薦企劃方向

## 10. Repo 規劃

MVP 採單一 monorepo，避免前後端、Agent、渲染與商家洞察服務在競賽時程中產生跨 repo 同步成本；各目錄日後可依擴縮需求獨立拆分。

| Monorepo 目錄 | 內容 | 對應原規劃 |
|---|---|---|
| `apps/web` | MVP Web 前端；第二階段再加入原生 App／AR 取景 | `tour-reel-studio-app` |
| `backend` | API、狀態機、專案與資產庫、Agent 執行層、Higgsfield adapter、FFmpeg 合成 | `tour-reel-studio-api`、`-agent`、`-render` |
| `intel` | 第二階段商家洞察服務與來源 adapter | `tour-reel-studio-intel` |
| `seed` | MVP Demo 專案的品牌資料、角色與實景照匯入腳本 | 新增 |
| `infra` | Docker Compose、反向代理與部署設定 | 新增 |
